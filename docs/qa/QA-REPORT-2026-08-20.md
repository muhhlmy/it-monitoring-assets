4. FINDINGS - CRITICAL
================================================================================

[CRIT-01] RBAC E2E Tests are FALSE POSITIVES
Severity:   CRITICAL
Module:     E2E Testing, RBAC
URL:        N/A (test infrastructure)
Evidence:   Database query confirms admin@admin.com and user@user.com DO NOT EXIST
            Admin/user auth state files are EMPTY (cookies: [], origins: [])
            E2E tests use ensureAuthenticated() fallback but accounts don't exist

Root Cause: Test accounts (admin@admin.com, user@user.com) defined in 
            e2e/fixtures/users.js do not exist in the database.
            The global-setup.js fails to create auth state for these accounts.
            RBAC tests check for ABSENCE of elements (e.g., "should NOT be visible"),
            so they pass even when the user is stuck on the /login page.

Impact:     All RBAC and permission tests are effectively untested.
            No verification that admin/user roles actually restrict access.

Fix:        1. Create admin@admin.com and user@user.com accounts in the database
            2. Set proper passwords matching e2e/fixtures/users.js
            3. Re-run global setup to regenerate auth state files
            4. Update RBAC tests to assert presence of role-specific elements,
               not just absence of forbidden elements

[CRIT-02] Default Password Hardcoded in Frontend HTML
Severity:   CRITICAL (Information Disclosure)
Module:     Import Modal (AppImportModal.vue:314-315)
Evidence:   Frontend source shows: "password: Password123!"
            Visible to anyone who can access the import page

Root Cause: AppImportModal.vue line 314-315 hardcodes the default password
            "Password123!" in the UI text that explains auto-created accounts.

Impact:     Default password for new employee accounts is publicly visible
            in the frontend HTML source. Attackers who gain access to the
            import page can learn the default password for all auto-created
            employee accounts.

Fix:        1. Move default password to backend environment variable
            2. Generate random unique passwords per imported user
            3. Display only after first login reset flow, not in static HTML
            4. Or: require password reset on first login

5. FINDINGS - HIGH
================================================================================

[HIGH-01] API Rate Limiter Too Permissive (600 req/min)
Severity:   HIGH
Module:     Backend Middleware
Evidence:   apiRateLimiter: 600 requests per 60 seconds per IP
            Login rate limiter: 10 per 15 min (reasonable)
            No 429 triggered after 20 rapid login attempts

Root Cause: apiRateLimiter (windowMs: 60000, max: 600) allows 10 req/sec.
            While loginRateLimiter is properly strict (10/15min), the general
            API limiter is generous enough for brute-force enumeration.

Impact:     API endpoints other than login are not protected against
            aggressive enumeration or DoS.

Fix:        Reduce apiRateLimiter max to 100-200 per minute, or add
            per-endpoint rate limits for sensitive operations.

[HIGH-02] Frontend Missing Security Headers
Severity:   HIGH (production only)
Module:     Frontend (Vite dev server)
Evidence:   curl -sI http://localhost:5173/ shows:
            - No Content-Security-Policy
            - No X-Frame-Options
            - No X-Content-Type-Options
            - No Strict-Transport-Security
            - No Referrer-Policy

Root Cause: Vite dev server does not add security headers by default.
            In production, this should be handled by nginx/CDN.

Impact:     Development environment is not representative of production
            security posture. If deployed without a reverse proxy, the
            frontend would be vulnerable to clickjacking, XSS, etc.

Fix:        Ensure production deployment adds security headers via
            nginx, Cloudflare, or similar reverse proxy.

6. FINDINGS - MEDIUM
================================================================================

[MED-01] No Server-Side Max Length Validation for Asset Name
Severity:   MEDIUM
Module:     Asset Controller
Evidence:   POST /api/assets with 500-character nama_asset returns 201
            (successfully created)

Root Cause: Asset controller does not enforce maximum length on nama_asset.
            The frontend may have a limit, but it's not enforced server-side.

Impact:     Potential for database bloat or UI overflow with extremely
            long asset names. No DoS risk due to PostgreSQL limits.

Fix:        Add max length validation in assetController.js (e.g., 255 chars).

[MED-02] Password Legacy Mode Support
Severity:   MEDIUM
Module:     passwordService.js
Evidence:   passwordService.js supports PASSWORD_LEGACY_MODE=verify-plaintext
            which allows plaintext password comparison.

Root Cause: Legacy support for migrating from plaintext to bcrypt passwords.
            If enabled, passwords are compared in plaintext using timingSafeEqual.

Impact:     If PASSWORD_LEGACY_MODE is accidentally enabled in production,
            plaintext password comparison would be used, bypassing bcrypt.

Fix:        Remove legacy mode after all passwords are migrated to bcrypt.
            Add a runtime check that logs a warning if legacy mode is active.

[MED-03] JWT Token Contains Permissions in Payload
Severity:   MEDIUM
Module:     Auth Controller
Evidence:   JWT token payload includes full permissions object:
            {permissions: {dashboard: "full", assets: "full", ...}}

Root Cause: authController.js sign() includes permissions in JWT payload.
            While verified server-side, it increases token size.

Impact:     Token size grows with feature count. Not a security issue since
            the token is signed and verified, but increases bandwidth.

Fix:        Consider storing permissions server-side only and fetching them
            from the database on each request, or use a separate claims model.

7. FINDINGS - LOW
================================================================================

[LOW-01] Inconsistent Error Messages
Severity:   LOW
Module:     Asset Controller
Evidence:   POST /api/assets with empty body returns "Hostname wajib diisi."
            even when nama_asset is the empty field.

Root Cause: Validation order: hostname is checked before nama_asset.
            The error message references the first failed field only.

Impact:     Minor UX confusion - user may fix wrong field first.

Fix:        Return all validation errors at once, or validate in logical order.

[LOW-02] No CSRF Token
Severity:   LOW
Module:     API
Evidence:   No CSRF token header in API responses.

Root Cause: JWT-based authentication (Bearer token) does not require CSRF
            tokens since cookies are not used for auth.

Impact:     None - this is expected behavior for JWT-based APIs.
